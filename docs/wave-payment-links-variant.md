# Variante avec liens de paiement Wave

Cette branche est une copie de la PR #5. Elle remplace, dans l'interface des paramètres Finance, la saisie des clés API par deux liens Wave Business : un pour la mensualité complète et un pour la demi-mensualité. À la création d'une cotisation exceptionnelle, un lien Wave propre à son montant est obligatoire. Le membre sélectionne son versement et ouvre le lien correspondant.

L'administrateur doit créer et vérifier dans Wave un lien distinct pour chaque montant. Les liens de type `https://pay.wave.com/m/M_ci_…/c/ci/?amount=1000` sont acceptés. L'application vérifie que le paramètre `amount` correspond au montant attendu ; cela ne garantit pas le montant réellement encaissé. Le membre doit relire le montant et le bénéficiaire dans Wave avant de confirmer. Si une cotisation exceptionnelle est partiellement réglée, son lien initial est masqué car il ne correspond plus au solde.

La première configuration fixe l'identifiant marchand Wave de l'association dans la base. Les liens mensuels et exceptionnels suivants doivent porter ce même identifiant, même si un administrateur efface les liens courants. La migration reprend cet identifiant depuis les liens existants et refuse de s'appliquer si plusieurs marchands sont déjà présents. L'association doit vérifier le bénéficiaire du premier lien directement dans Wave : l'identifiant dans l'URL ne prouve pas à lui seul la propriété du compte.

Dans Paramètres → Paiements Wave, un administrateur peut demander un changement de marchand avec les nouveaux liens mensuels. Un **autre administrateur actif** de la même association vérifie le bénéficiaire dans Wave et approuve ou refuse la demande. Une association avec un seul administrateur actif doit d'abord ajouter un second administrateur ; l'auteur ne peut pas valider sa propre demande. À l'approbation, le nouveau marchand et les liens mensuels sont activés ensemble, la demande garde les identités du demandeur et du validateur, et tous les anciens liens exceptionnels sont retirés. Les cotisations exceptionnelles non échues et encore impayées apparaissent alors dans les paramètres pour ajouter leurs liens du nouveau marchand. Tant que ces liens ne sont pas ajoutés, les membres ne peuvent pas lancer de paiement Wave pour ces cotisations.

Cette validation à deux administrateurs réduit le risque d'une session administrateur compromise, mais elle ne prouve toujours pas la propriété du compte marchand. En particulier, si un administrateur peut créer ou contrôler un autre compte administrateur, l'approbation ne garantit pas deux personnes indépendantes. Le bénéficiaire doit être contrôlé dans Wave avant validation ; une vérification indépendante plus forte ou l'API Wave serait nécessaire pour un contrôle entièrement automatisé.

Ouvrir le lien ne prouve pas que le paiement a abouti. La comptabilité reste mise à jour par l'administrateur après vérification du paiement reçu. Les anciennes tables et fonctions de clés API sont conservées pour que cette branche reste compatible avec le schéma issu de la PR #5, mais leur configuration n'est plus proposée dans l'interface.

La page Finances → Comptes marchands Wave permet de tenir un registre manuel séparé pour le compte actuel et les anciens comptes. Les administrateurs saisissent un solde initial et des mouvements référencés, puis comparent le solde calculé au relevé Wave. Une écriture est immuable ; une erreur se corrige par une écriture inverse. Le registre ne récupère pas le solde réel et n'attribue pas automatiquement les anciennes cotisations à un marchand, car cette attribution serait incertaine après un changement de compte.

Appliquer les migrations `202610120001_wave_payment_links.sql` à `202610120004_wave_merchant_rotation.sql` avant de tester cette variante. Aucun lien réel, identifiant marchand ou secret n'est ajouté au dépôt.
